# 委派与上下文交接规则

本文件是写作委派条件的唯一依据。先明确交付范围并规划写作批次，再决定如何执行；skill 加载和子代理调用是两件事。独立审核器仍只在明确需要时调用。

## 1. 顺序判定

按交付范围顺序判定，课程单元数、文件数和页数均不作为固定委派门槛。

1. 用户明确指定就地完成或使用子代理：采用用户指定模式。用户要求就地完成时，主编排器仍逐写作批次推进。
2. 未指定模式，且任务只交一个指定正文片段，或只修订已有笔记的指定段落、公式、表格：主编排器就地完成。该分支没有从完整课件重新盘点、生成整章或整本指南的职责。
3. 未指定模式，且任务是从课程材料生成、重构或续写整章/整本复习资料：委派综合写作器，主编排器负责来源清单、分批计划与统稿。无论课程将材料称为一个单元还是多个单元，都按此分支执行；同一种写作器可启动多个实例，按下文的批次依赖规则调度。
4. 需要委派但环境没有可用的子代理工具，或调用被权限拒绝：记录实际原因，转为 local-fallback，按相同写作批次就地完成。普通执行错误先定位并修复；不能把任务复杂、遗漏任务包或未注册专用 agent 当作工具不可用。

所有就地模式均先读取 study-note-unit-writer/SKILL.md 及其 references/unit-writing.md。在 synthesis_plan.md 记录交付范围、execution_mode（local / delegated / local-fallback）、用户覆盖指令（若有）、选择原因和各批次进度。范围改变时先更新计划再重新判定，保留已完成片段；执行方式不因模型临时偏好改变。

| 未指定模式时的任务 | 执行结果 |
| --- | --- |
| 课程称为一个单元，课件约 200 页，生成该单元复习资料 | 委派；先按子主题和模型阶段规划多个写作批次 |
| 整理一个短课件，交付完整复习指南 | 委派；可只有一个写作批次，不按内容类型另派代理 |
| 重写已有笔记的某个推导或比较表 | 就地；沿用已有定义、记号与正文标签 |
| 大范围任务，用户要求不要子代理 | 就地；仍分批写、维护交接记录并统一去重 |

## 2. 课程单元与写作批次

课程单元是原课件的章节或教学划分，可以有一两百页和许多小节。写作批次是一次任务包的范围：围绕一个连贯的学习问题、模型结果或推导阶段，交付一份正文片段与交接 JSON。现有文件名和 JSON 中的 unit_id 标识写作批次，不代表整个课程单元；同一课程单元可以对应多个 unit_id，计划中记录其共同的课程单元/章节及正文顺序。

先逐项盘点内容，再在自然的子主题、模型结果或推导阶段之间分批。每批列明对应证据范围、必留结果、前置定义与交叉引用。若计划中的一次任务仍包含多个可独立讲解的问题或不同模型结果，继续拆分任务包；不要把整份长课件当作一个写作任务。一个长证明可按准备引理、核心证明与后续推论分批，衔接处保留已证结论及成立条件。

定义、推导和必要图表在同一批次内协作成文，不按内容类型切开。依赖已有模型的批次继承已确认设定，只写新增结论、变化的假设与关键步骤；原课件重复回顾页可对应同一已有正文位置。批次边界用于安排执行，不强制产生新的正文标题、结论框或公式表。完整知识点与关键推导仍由来源清单逐项追踪。

## 3. 按依赖调度

主编排器先统一公共定义、记号、结果键及其正文归属，在 synthesis_plan.md 为各批次记录 depends_on、负责新建的定义、输出路径和 agent ID。共享基础内容先由主编或前置写作批次建立并确认，随后发给各写作器相同的相关上下文。每个知识点的主要讲解位置明确归属一个批次，其他批次引用它。

有多个前置条件已确认、范围互不重叠的批次时，默认并行派发多个综合写作器实例；依赖未完成结果的批次等待其前置批次被主编接收。同一实例一次承担一个批次。并发数量按可独立开展的工作、用户要求和环境容量决定，不设置课程单元数、页数或固定代理数门槛，也不为凑并行拆碎连贯推导。

主编按完成情况接收正文和交接，更新共享记录并派发已具备条件的后续批次；不等待无关批次全部完成。各写作器只编辑独占的正文片段和交接文件，新建标签使用任务包分配的批次前缀，继承标签保持原名。来源清单、计划、continuity.md、issues.json、总稿与公式汇总仅由主编修改。

例如先完成潜在结果框架与共同记号，再并行安排 RCT 和 RDD；各主题内部存在推导依赖的批次仍顺序推进。教学顺序决定最终正文顺序，代理完成先后不改变它。若公共定义或前置结果发生修正，主编通知受影响的写作器更新对应片段，再接收其结果；无关批次继续执行。

## 4. Claude Code 调用

委派分支通过环境实际提供的子代理工具调用写作器，当前 Claude Code 使用 Agent，旧版本可能显示 Task。若会话中注册了 study-note-unit-writer 子代理，使用它；否则使用可写文件的 general-purpose 子代理，在任务包中提供写作 skill 与参考文件的绝对路径，并要求先读取。仓库的 .claude/agents/study-note-unit-writer.md 是原生注册定义；agents/openai.yaml 仅为 Codex 元数据。

并行派发使用环境实际提供的并发或后台调用能力，先启动就绪批次，再接收完成结果；不要每派发一个独立批次就同步等待它写完。若环境只支持串行调用，记录该限制并按依赖推进。

加载或输入 /study-note-unit-writer 本身不能作为“已委派”的证据。记录实际调用返回的 agent ID。独立分支使用不同写作器实例；同一依赖链上共享设定的后续批次优先恢复已空闲的写作器，使用本会话提供的恢复能力。新调用若不携带恢复标识，按新上下文处理，重新提供任务包。连续性以文件记录为准，不要求一个代理一直携带全课程历史。

依赖本批次的后续任务在两份文件完成并经主编接收后才派发；独立批次按上文并行调度。部分结果或中断不算完成；继续该任务，完成前保持 drafting 状态，不阻塞无关分支。整本统稿与编译由主编排器负责。

需要独立审核时，优先调用已注册的 coverage-audit-note-reviewer 子代理；未注册时使用可读取材料的通用子代理。任务包提供审核 skill、audit-protocol.md 与所需材料的绝对路径。写作器的自查不充当独立审核。用户指定就地完成或环境无法委派时，由主编排器自审并说明没有独立复核。

## 5. 文件维持连续性

主编排器保留 source_inventory.md、synthesis_plan.md、continuity.md 和全部单元文件。continuity.md 只记录可复用的定义、记号、结果键、正文标签及所属单元，不复制整段正文。

每个任务包包含本单元证据、必留结果、派发时已确认的相关定义和记号、前置结果与标签，以及本单元负责新建的定义。附上明确的正文与交接输出路径。写作器将新增或修订的连续性条目放入 handoff 的 continuity_updates；主编排器核对并更新 continuity.md 后，才将该结果交给依赖它的批次。

父会话接收文件路径、覆盖 ID、未决问题与必要的连续性变动，不要求子代理把全文再贴回对话。主编排器最终仍逐单元读取真实正文完成合并与语义去重；文件与标签保证可追踪，不要求所有正文一直驻留在同一上下文中。

## 6. 完成条件

就地、委派和降级模式都交付相同的正文片段、交接记录、全书公式筛选与覆盖对应表；均保留最终编译和结构/PDF 审核步骤。独立审核器可省略不等于主编排器自审可省略。用户明确暂缓测试或编译时，记录待执行项目并交付未验证草稿，不能声称通过验收。

机制依据：[Claude Code 子代理](https://code.claude.com/docs/en/sub-agents)与[Skills](https://code.claude.com/docs/en/skills)。模式规则是本项目约定，不是 Claude Code 自动保证的强制门禁。
